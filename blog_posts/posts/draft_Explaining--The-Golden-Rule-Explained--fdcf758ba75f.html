Explaining ‘The Golden Rule Explained’


Rebasing a branch with Git is a much misunderstood topic. The Golden Rule of rebasing is to never rebase a shared branch. That’s a great maxim, but why not? And how could a team get into that state? 

Pierre de Wulf’s recent article is one of the better explanations of what Git sees when two or more people rebase a shared branch. The article has some great graphics, and the concepts are clear. However, in order to really grasp what was going on I wanted to know what was happening on the command line. Exactly what were the (mis)steps the fictional developers Anna and Bob took that led them to violate the Golden Rule of Rebase? To that end I wrote up this code based walk through which tracks the misadventures of Anna and Bob as described by Wulf. 

The story below will make the most sense if read in conjunction with the original blog post at: https://medium.freecodecamp.org/git-rebase-and-the-golden-rule-explained-70715eccc372.

Wulf tells the tale of developers Anna and Bob who are both working on a project together. Let’s recreate the setup on a single Linux box for simplicity. We will need three repos: ‘ghub’, a shared repo; ‘anna’, for Anna’s code; and ‘bob’, for Bob’s work. 

The next few lines set up the shared repo: git init ghub then add a couple of commits: cd ghub ; for f in a b ; do touch ${f} ; git add ${f} ; git commit -m “Add ${f}” ; done We create a new branch: git checkout -b feature ; for c in d ; do touch ${c} ; git add ${c} ; git commit -m “Add ${c}” ; done After moving back to the master branch and adding a new commit: git checkout master ; for c in c ; do touch ${c} ; git add ${c} ; git commit -m “Add ${c}” ; done 

Now we clone the repo twice once each for Anna and Bob: cd .. ; for r in anna bob ; do git clone ghub ${r} ; done
